# API Sentinel — API Key Detection Dataset Guide

## 1. Overview & Purpose

The **API Key Detection Dataset** is a purpose-built security benchmark dataset engineered for **API Sentinel**. It contains **10,000 carefully curated and normalized samples** focused strictly and exclusively on **API keys and API tokens**.

Unlike generic secrets repositories, this dataset excludes passwords, certificates, private SSH keys, and database connection strings to provide an accurate, high-fidelity benchmark for API credential leakage detection.

## 3. Normalized Schema Specification

Every sample across all JSONL files conforms strictly to the following normalized JSON schema:

```json
{
  "sample_id": "sample_aws_pos_0001",
  "sample": "aws_access_key_id = \"AKIA2OGYBAH6UREMKH4Q\"",
  "provider": "aws",
  "key_type": "api_key",
  "label": "positive",
  "is_synthetic": true,
  "format_valid": true,
  "source": "custom_synthetic",
  "source_reference": "GitHub Supported Secret Scanning Pattern (aws)",
  "license": "Internal Synthetic Dataset (API Sentinel Evaluation License)",
  "notes": "AWS 20-character Access Key ID"
}
```

### Allowed Values
- **`label`**: `"positive"` (valid API key signature) | `"negative"` (hard negative lookalike)
- **`key_type`**: `"api_key"` | `"api_token"`
- **`is_synthetic`**: `true` (generated by deterministic generator) | `false` (de-identified upstream sample)
- **`format_valid`**: `true` | `false`

## 4. Context Wrapping & Difficulty Engineering

Real-world API leaks rarely occur as bare strings. The dataset embeds tokens within realistic code and configuration envelopes:
- **Raw token**: Pure credential string
- **Python / JS assignment**: `api_key = "..."`, `const apiKey = "...";`
- **JSON payload**: `{"service": "production", "api_key": "..."}`
- **Environment variables**: `export OPENAI_API_KEY="..."`, `AWS_ACCESS_KEY_ID=...`
- **HTTP Headers**: `Authorization: Bearer ...`, `X-API-Key: ...`
- **YAML / Config**: `credentials:\n  token: ...`
- **cURL commands**: `curl -H "X-Api-Key: ..." https://api.internal/`

### Hard Negative Lookalikes
Negative samples test the detection engine against realistic non-secret tokens:
- Truncated prefixes (`AKIA`, `sk-`, `ghp_`)
- Misspelled prefixes (`aiza_`, `sk_live-`, `nv_api_`)
- Standard UUIDs (`d3b07384-d113-46ec-9cdb-1e7fffe50fba`)
- Cryptographic digests (MD5, SHA-1, SHA-256)
- Documentation placeholders (`YOUR_API_KEY_HERE`, `<OPENAI_API_KEY>`)
- Variable declarations and public IDs (`pk_live_...`, `AC...` Twilio Account SID)

## 5. Train / Validation / Test Splits

The dataset is partitioned using a deterministic random seed (`42`) stratified across providers and positive/negative labels:
- **Training Split (70%)**: `dataset/splits/api_keys_train.jsonl` (7,000 samples)
- **Validation Split (15%)**: `dataset/splits/api_keys_validation.jsonl` (1,500 samples)
- **Held-Out Test Split (15%)**: `dataset/splits/api_keys_test.jsonl` (1,500 samples)
- **CSV Equivalents**: Provided alongside every JSONL file for data science and analysis workflows.

**Zero Data Leakage:** Sample SHA-256 hashes are strictly verified to ensure zero overlap across splits.

## 6. How to Regenerate the Dataset

To regenerate the dataset from scratch using the deterministic pipeline:
```bash
python backend/scripts/generate_api_key_dataset.py
```
This will rebuild `api_keys_master.jsonl`, all 3 splits, and refresh `metadata/dataset_cleaning_report.json` and `metadata/dataset_split_metadata.json`.

## 7. Active Security Testing Integration (Modes A & B)

The 10,000-sample dataset directly powers active security detection testing in API Sentinel through two decoupled operational modes:

### Mode A: Single Sample Testing (Default)
Allows security engineers and developers to test exactly **one** API key sample at a time:
- **Provider & Label Filtering:** Select specific providers (e.g., AWS, OpenAI, Stripe) or sample categories (`positive` vs `negative`).
- **Protected Masking Preview:** Samples are rendered exclusively in masked form (`sk-ab...12cd`). Raw tokens are never sent over the wire or stored.
- **Explainability:** Upon execution, the detection engine outputs:
  - Expected Provider vs Detected Provider
  - Expected Label vs Predicted Label
  - Standardized outcome badge (`correct_detection`, `false_positive`, `false_negative`, `correct_rejection`)
  - Execution time in milliseconds (typically 0.05–0.15 ms)
  - Detection reasoning: exact signature regex matched and Shannon information entropy score.
- **Persistence & Stepping:** Each test run is recorded in SQLite (`dataset_test_sessions` & `dataset_test_results`), and a **"Next Sample"** button enables seamless stepping through the dataset.

### Mode B: Batch Testing
Executes comprehensive detection across configurable slices (10 to 500 samples):
- **Concurrency Guard:** Thread-safe lock (`_batch_lock`) prevents overlapping batch operations, returning HTTP 409 Conflict if a test is already running.
- **Real-Time Progress & Metrics:** Computes TP, FP, TN, FN, Precision, Recall, F1 Score, Overall Accuracy, and per-provider performance breakdown.
- **Sample Explorer:** Inspect individual sample predictions, execution durations, and outcome classifications directly in the UI.

---

## 8. Test History & Audit Trail

All Single and Batch test sessions are recorded in SQLite:
- `dataset_test_sessions`: Stores mode, parameters, sample counts, duration, and performance metrics.
- `dataset_test_results`: Stores individual test records, ground truth, predictions, outcomes, masked strings, and explanations.
- API Endpoints:
  - `POST /api/dataset/test/single`: Run single test
  - `GET /api/dataset/test/sample/{sample_id}`: Inspect masked sample
  - `POST /api/dataset/test/batch`: Run batch test
  - `GET /api/dataset/test/batch/{session_id}`: Query batch status
  - `GET /api/dataset/test/batch/{session_id}/results`: Query paginated batch results
  - `GET /api/dataset/test/history`: Retrieve past testing sessions
